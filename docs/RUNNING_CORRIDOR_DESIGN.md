## 4. 왕복(retrace) 판정과 회랑의 충돌 — 수치

선형 회랑(하천·강변)의 자연스러운 코스는 **out-and-back**(가서 되돌아옴). 그러나:
- out-and-back 길이 L → **turnaround가 전체를 되밟아 `longest_retrace_m ≈ L/2`**.
- target 3km → 1500m · 5km → 2500m · 8km → 4000m. **전부 `_OVER_SERVE_MAX_SPUR_M=800`·`_FLOOR_SPUR_M=1200` 초과.**
- **≥1.6km out-and-back은 100% longest_retrace>800** → missed-serve 제외, in-band여도 `park==0 & longest>1200`면 **floor 재추첨으로 능동적으로 회랑을 버림**(`route_service.py:1471-1492`).
- SQ1 `retrace_ratio`도 out-and-back은 **≈1.0**(전체 왕복) → 최악 점수.

→ **역설: 가장 좋은 러닝 경험(하천변 왕복)을 "최악 스퍼"로 취급해 탈락**시킨다. 반면 두 사례의 **도로 순환**은 retrace 0.26/0.21·longest 783/171로 **게이트 통과**. 품질 지표가 **running 경험과 역상관**.

**"러닝 길 위의 왕복" vs "골목 막다른 가지" 구분 제안**(3신호):
1. **되밟는 구간의 길 종류**: 하천변/보행전용(청계천로·한강공원·roadType 21+회랑 멤버십) 위의 왕복 = 정상 / 도로·골목 위 스퍼 = 벌점. (T-map `road_segments` roadType + 회랑 데이터로 판정 — §5a.)
2. **run 개수(branch_count)**: out-and-back은 **긴 run 1~2개** / 골목 가지는 **짧은 run 多**(성북동 10·한남 14). → `branch_count` 높으면 가지, `longest_run`만 크고 branch 적으면 왕복.
3. **왕복이 본체인가 곁가지인가**: retrace_ratio 高 + branch 低 + 회랑 위 = 정식 왕복 / retrace 中 + branch 高 + 도로 = 나쁜 스퍼.
→ **판정식 초안(관측 후 확정)**: `되밟기 구간의 ≥80%가 회랑/보행전용 AND branch_count ≤ 2` 면 out-and-back을 **정식 유형으로 허용**(longest_retrace 게이트 면제).

## 5. 개선안 비교

### (a) 서울 주요 러닝 회랑 데이터 보유 + 회랑 후보 강제·우대
- **내용**: 한강(본류+지천)·청계천·중랑천·양재천·탄천·안양천 등 **연속 polyline을 데이터로 보유**. 출발점이 회랑 Xm 내면 **회랑을 타는 후보(왕복 또는 회랑 경유 루프)를 반드시 생성·우대**.
- **데이터/라이선스**: ⑴ **서울 열린데이터광장**(하천·보행로·자전거도로 GIS) — 대개 **CC BY(출처표시)**, 상용 가능. ⑵ **OSM** waterway/footway — **ODbL**(출처표시+share-alike 주의). ⑶ NGII. **미확인**: 각 데이터셋 정확 라이선스·상용 조건은 출시 전 실확인.
- **구현 규모 M~L**: 회랑 테이블(또는 `app/data` GeoJSON) + 근접 매칭 + 회랑 후보 빌더. **요청당 추가**: 인메모리 근접 1회(+0ms) + 회랑 후보 T-map 스냅 1~2콜(+T-map). 
- **기존 문서 관계**: canonical(닫힌 루프)의 **선형판 확장**. 앵커 `_WATERFRONT`(점 POI)를 **연속 geometry로 대체·보강**. ROUTE_NEAREST_SERVE 후보 풀에 합류.

### (b) 후보 점수에 "러닝 친화 구간 비율" 추가
- **내용**: 후보의 `friendly_ratio` = (보행전용 21 + 공원/하천변 회랑 멤버십 길이) / 총길이. 점수/tiebreak에 반영(대로 22·23 비율 높으면 벌점).
- **데이터**: **이미 수집됨** — `gen_meta.tmap_road_types`(roadType별 길이) + (a)의 회랑 멤버십. 추가 호출 **0**.
- **구현 규모 S**: 점수 축 1개 추가. **요청당 추가**: 0(road_segments 이미 페치).
- **기존 문서 관계**: ROUTE_SHAPE_QUALITY에 품질 축 추가, park_coverage 보완. 두 사례(한남 41% 대로)를 바로 강등.

### (c) 선형 회랑에서 왕복 코스를 정식 유형으로 허용
- **내용**: §4 판정식(되밟기 ≥80% 회랑 위 + branch≤2)이면 **out-and-back을 정식 코스로 서빙**(longest_retrace 800 게이트 면제·SQ1 벌점 면제). "골목 가지"는 여전히 벌점.
- **데이터**: (a)회랑 데이터 + T-map road_segments. 추가 호출 **0**(판정만).
- **구현 규모 M**: retrace 분류(회랑 멤버십) + 게이트 분기. **요청당 추가**: 0.
- **기존 문서 관계**: §4 충돌을 직접 해소. ROUTE_SHAPE_QUALITY 게이트·ROUTE_NEAREST_SERVE 서빙 분기 수정.

**추천 조합 = (a)+(b)+(c)**: (a)로 회랑 데이터·후보를 만들고, (b)로 도로 순환을 강등, (c)로 회랑 왕복을 살림. **+ 별건 즉효**: `_serveable_over_cap`의 앵커 제외를 재검토(수변 앵커가 missed-serve에서 사장되는 §2ⓐ 구멍 — 회랑 후보엔 이 제외를 풀어야 함).

## 7. 오너 결정 + 작업 순서 추천

1. **회랑 데이터 소스**: 미확인 — 추천 **서울 열린데이터(CC BY) 1차 + OSM 보조**. 이유: 상용 가능·출처표시, 한강/하천 커버.
2. **회랑 보유 범위**: 미확인 — 추천 **한강 본류 + 청계천·중랑천·양재천·탄천·안양천 + 주요 공원**. 이유: 서울 러닝 수요 집중.
3. **앵커 missed-serve 제외 해제?**(§2ⓐ): 미정 — 추천 **회랑 후보 한정 해제**. 이유: 수변 후보가 missed에서 사장되는 구멍 봉합(일반 앵커 제외는 유지).
4. **out-and-back 허용 판정식 임계**: 미정 — **관측 후 확정**(되밟기 회랑 비율·branch_count 임계). 이유: 추측 컷 금지(§B).
5. **friendly_ratio 점수 가중치**: 미정 — **관측 후 확정**. 이유: 분포 보고 보정.
6. **회랑 후보 강제 생성 트리거 거리**: 미정 — 추천 **출발점 회랑 ≤800m**(canonical 진입권과 동형). 이유: 일관성.

**작업 순서 추천**(현 순서 = 가까운 코스 서빙 S2/S3 → 언덕 H1): **S2/S3 → 러닝 회랑(a+b+c) → 언덕(H1)**. 근거: 두 사례는 **품질 체감 악화의 핵심**이고 (b)(c)는 S2/S3의 품질 게이트·서빙 분기에 자연 합류(함께 하면 중복 작업↓). (a) 회랑 데이터는 별도 데이터 프로젝트라 병렬 착수 가능. **언덕(H1)보다 러닝 회랑 우선** 권고(제보 빈도·체감 큼).
