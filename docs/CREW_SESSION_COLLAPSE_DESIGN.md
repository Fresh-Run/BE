# 크루 세션 접기 설계 — 대형 크루(30~50명) 정기런 카드 도배 방지

> 상태: **설계만 — 오너 승인 대기, 구현 착수 금지.** 2026-08-01.
> 현 구조: 크루 피드는 플랫 카드(런당 1장), session_key 서버 자동 파생 수렴,
> is_crew_session·session_participant_count는 이미 행마다 계산됨.
> 문제: 50명 정기런이면 동일 배지 카드 50장이 피드를 도배.
> 핵심 발견: **session_key가 응답에 미노출**(내부 전용) — 클라가 접고 싶어도
> 그룹 키가 없다. 이 공백 하나가 전략 선택을 좌우한다.

## 1. 표현 전략 비교

### ⓐ 클라 그룹핑 (서버는 session_key 필드 1개만 additive 노출) — **추천**

- 서버: `CrewRunItem.session_key: Optional[str]`(미태그 null) 노출이 전부.
  플랫 응답·limit/offset·정렬 전부 불변 — **페이지네이션 시맨틱 무변**.
- 클라: 같은 session_key 행을 접어 카드 1장. 카드의 "N명 참여"는 행마다
  이미 실려 오는 `session_participant_count`(서버 **전역** 계산 — 페이지에
  로드된 행 수가 아님)를 그대로 쓰므로 **첫 행만 받아도 카드 수치가 완전**하다.
- **50행 세션이 limit=20 페이지를 관통할 때**: 온전한 접기를 "전 페이지 로드
  없이 완성"하는 건 불가능하다 — 정직하게 불가능이라고 명시한다. 단 실사용
  시맨틱은 성립한다:
  1. 카드 수치(N명 참여)는 전역값이라 첫 조우 시점부터 정확(성장 없음).
  2. 후속 페이지에서 같은 키 행이 오면 **기존 카드에 흡수, 신규 카드 생성
     금지**(클라 소비 규칙로 박제 — 이게 유일한 계약 문구).
  3. 정기런 행들은 ran_at이 시간대에 몰려 사실상 연속 배치 — 관통은 경계
     1회 수준이고, 흡수 규칙이면 UX 결함이 아니라 "페이지가 짧아 보임" 정도.
- 장점: **답글 때 확립한 "플랫+참조, 그룹핑은 클라" 패턴과 동일 축**(2026-08-01
  parent_comment_id 전례). 서버 위험 0·쿼리 0·계약 위험 0.
- 한계: 접힌 카드의 "대표 유저 아바타 N명"은 로드된 행 범위에서만(§2).

### ⓑ 서버 세션 요약 카드

- 신규 파라미터(`collapse=sessions`)에서 응답 항목이 "런 행 또는 세션 요약
  행"의 혼합 타입이 됨 — limit은 **항목(entry) 단위** 재정의.
- 세션 단위 페이지네이션 계약: 정렬 키를 "세션은 max(ran_at), 단독 런은
  ran_at"으로 통일한 entry 목록에 limit/offset. 서버는 후보 창을 크게 스캔해
  그룹핑 후 슬라이스해야 하므로(그룹이 창 경계에 걸리는 문제) 사실상
  **전 윈도우 스캔 + keyset 전환 압박 가중**. 펼침은 별도 API 필요(§ⓒ).
- 단점: 혼합 타입 스키마(신규 카드 shape), 대표 유저 서버 조립(쿼리 추가),
  30~50명 규모에 과설계. 장점: 클라 로직 최소.

### ⓒ 혼합 (요약은 서버, 펼침은 기존 플랫 재사용)

- ⓑ의 요약 + 펼침은 `GET /crews/{id}/runs?session_key=...`(additive 필터
  파라미터)로 기존 플랫 shape 재사용. ⓑ보다 API 수는 절약되나 ⓑ의
  페이지네이션 신계약·혼합 타입 문제는 그대로 상속.

**추천: ⓐ** — 근거: ①패턴 일관(답글 "플랫+참조" 직후에 같은 문제를 다른
방식으로 풀면 Ivan 소비 모델이 갈라진다) ②서버 필드 1개 additive로 위험 0
③참여자 수가 이미 전역 계산이라 클라 접기의 최대 약점(수치 부정확)이 애초에
없다 ④30~50명 규모에서 ⓑⓒ의 신계약 비용이 실익을 초과. ⓑ는 크루가
수백 명 규모가 되고 "피드 첫 페이지가 요약만으로 구성돼야" 할 때 재검토.

## 2. 대표 유저 선정 (접힌 카드의 아바타 N명)

- **ⓐ에서는 서버 결정이 불필요** — 클라가 로드된 행에서 앞 N명(=ran_at
  최신순 선착)을 쓰면 된다. 단순 해법 우선.
- 서버 선정이 필요해지는 건 ⓑⓒ뿐. 그 경우의 후보: 선착순(단순·추천) /
  크루 운영진 우선(권위 표시) / 팔로우 우선(개인화 — 캐시 불가·비용 최대).
  → **오너 결정 지점 ①**로 분리(지금은 결정 불요 — ⓐ 채택 시 소멸).

## 3. 세션 정밀도 — 조별 정기런(아침/저녁) 문제

- 현 키: `a:{공지id}`(정밀) / `c:{크루id}:{KST날짜}`(날짜 버킷). 대형 크루가
  하루 2회(아침조/저녁조) 뛰면 **날짜 버킷에선 한 세션으로 합쳐진다**.
- 해법 비교:
  - **공지 기반 시작 유도(추천)**: 조별로 집결 공지를 만들면 `a:` 키로 이미
    정밀 분리된다 — **키 설계 변경 0·하위 호환 문제 0**. 대형 크루의 조별
    운영은 어차피 공지(집결 시간·장소)가 자연스러운 운영 단위. 필요한 건
    클라 UX(공지에서 "크루 러닝 시작" 진입 시 announcement_id 동봉 — 이미
    계약에 있음)와 크루장 안내뿐.
  - 키 보강(시간 창: `c:{crew}:{date}:{am|pm}` 등): 기존 키와 혼재(하위 호환
    처리 필요), 경계(11:59 시작 조) 새 엣지, 창 폭이라는 새 매직넘버 —
    **기각 근거로 박제**. 공지 유도로 안 풀리는 실사례가 관측되면 재검토.
- 표시 구분: session_key가 노출되면 클라가 접두(`a:`/`c:`)로 "공지 정기런" vs
  "즉흥런" 배지를 나눌 수 있다 — 서버 추가 작업 0. 접두는 이미 안정 계약
  (파생 규칙 무변경이 하위 호환의 전부).

## 4. 계약 원칙 (additive 경로)

- 변경은 **`CrewRunItem.session_key: Optional[str]` 필드 1개** — 기존 플랫
  소비 클라는 모르는 필드 무시로 무영향. 파라미터 추가 없음(ⓐ).
- **상속 주의**: ActivityFeedItem(K1)이 CrewRunItem을 상속하므로 필드가 K1
  피드에도 자동 노출된다. session_key엔 crew_id가 포함되는데 crew_id는
  공개 식별자라 유출 민감도는 낮으나, K1 문맥에선 무의미한 필드다 —
  **구현 시 크루 피드 조립에서만 채우고 K1 조립은 미채움(null)** 권장
  (kudos 승격 때와 동일하게 필드는 부모, 값 채움은 서피스별).
- 답글 패턴과의 일관성: "서버는 플랫+참조 키, 그룹핑·스레딩은 클라" — 동일.

## 5. 성능

- ⓐ: 추가 쿼리 **0** — session_key는 피드 쿼리 select에 이미 포함
  (crew_service.py 조립부), 응답 필드에 옮겨 적기만. 참여자 수도 기존 배치
  1쿼리(`_session_participant_counts`) 그대로. 50명×여러 세션 페이지에서도
  현행과 동일 상한(limit≤100 행 + 배치 헬퍼 고정 쿼리 수 — 크루 kudos 전례).
- ⓑⓒ였다면: 대표 유저 조립 배치 1쿼리 추가 + 그룹핑 창 스캔 — 기각 사유의
  일부.

## 6. 롤아웃

1. **계약 선박제**(어드바이저→Ivan): 필드 1개 + 소비 규칙 3줄(같은 키 접기 /
   후속 페이지 흡수·신규 카드 금지 / `a:`·`c:` 접두 구분) + participant_count
   전역 시맨틱 재확인.
2. 서버 1커밋: 필드 노출(+K1 미채움) + 테스트 — **플래그 불요**(additive
   필드는 소비 전까지 무영향, 롤백=필드 제거 아닌 클라 미소비).
3. Ivan UI 작업과 병렬 — 서버 선배포 가능(필드가 먼저 나가도 무해).
4. 테스트 스케치: 크루 피드에 session_key 실림(태그런)·null(일반런) /
   같은 세션 2유저 행의 키 동일 / K1 피드에선 null / 기존 키 셋 불변(회귀) /
   session_only 뷰 동일 필드.

## 7. 오너 결정 필요 지점

1. **전략 채택** — 추천 ⓐ(필드 1개+클라 접기). ⓑ 요약 카드는 수백 명 규모
   신호 시 재검토 트리거로만.
2. **조별 정기런** — 추천 "공지 기반 시작 유도"(키 변경 0). 크루장 안내
   문구/UX는 Ivan 레인.
3. (ⓐ 채택 시 소멸) 대표 유저 서버 선정 기준 — ⓑⓒ에서만 필요.

## 8. 결정 이력 (§F — 결정 · 근거 · 재검토 트리거)

- **클라 그룹핑 + 필드 1개 노출(제안)** · 근거: 참여자 수 전역 계산 기존재·
  답글 패턴 일관·계약 위험 0 · 재검토: 크루 100명+ 또는 "첫 페이지 요약"
  요구 시 ⓑ.
- **날짜 버킷 유지, 조별은 공지 유도(제안)** · 근거: 키 하위 호환 0비용,
  공지가 자연 운영 단위 · 재검토: 공지 없이 조별 운영하는 크루 실관측 시.
