# in-band spur 구제(INBAND_SPUR_RESCUE) 설계 — v87 hit의 L>800 재추첨 유도

> 상태: **승인·구현됨(2026-07-30)** — 오너 결정: ①상한 800 ②클라 통지 없음
> ③관측은 engine 무관, **구제 트리거는 v87 한정**(앵커는 L 기록만 — 확장은
> 실측 후 별도 판정, §7-3 갱신) ④재추첨 결과는 **개선만 반영**(L≤800 강제
> 아님, §7-4 채택). 플래그 OFF 상태로 배포 대기.
> 발단: 오산 실주 피드백(rladbgns1022) → v87 in-band hit 65건 실측에서
> longest_retrace_m(이하 L) 중앙값 539 · p75 981 · p90 1806 · max 3366.
> spur 상한(`_OVER_SERVE_MAX_SPUR_M=800`)이 over-cap(missed) 경로에만 걸려
> **in-band "hit"는 L 무제한**인 설계 공백이 일상 품질 문제로 확정됨.
> 방향(오너): 하드 차단 기각(실유저 서빙 −23%) — "L>800이면 재추첨 유도,
> 끝까지 못 살리면 그중 최선(원 후보 포함)을 그대로 서빙".

## 0. 요약

- **2단 구제**: ①0원 대체(같은 풀의 다른 in-band 후보 중 L≤800 재선택, Gemini
  0콜) → ②구제 재추첨(별도 축소 풀 N롤, 기본 5) → ③전패 시 **L 최소인 후보
  (원 후보 포함)를 그대로 서빙**. 서빙 건수는 어떤 경로에서도 기존과 동일.
- 예산: **별도 +N롤** (기존 9롤 풀은 선지급 고정이라 "잔여 예산"이 구조상 없음).
  비용 추정 상한 **+32%/일** (5롤 기준, ①단계 성공률 0 가정) — §2.
- 플래그 `SPUR_RESCUE_ENABLED` 기본 OFF (ANCHOR_POOL_N 전례, `app/core/config.py:55`).
  OFF면 현행 코드 경로와 바이트 단위 동일 동작.

## 1. 트리거·예산

### 1.1 트리거

메인 흐름의 in-band 승자 확정 직후(`route_service.py:1144` `_best_in_band` 뒤):

```
발동 조건 = (플래그 ON) and (best가 in-band "hit") and
            (_spur_metrics(best.polyline)["longest_retrace_m"] > SPUR_RESCUE_MAX_M)
```

- `SPUR_RESCUE_MAX_M` 기본 800 — over-cap 경로의 `_OVER_SERVE_MAX_SPUR_M`(:179)과
  동일 값. 두 상수는 의미가 같으므로 구현 시 **단일 소스**(§B 공유 로직 규칙)로
  통일하되 설정 분리는 유지(in-band 쪽만 플래그로 끌 수 있게).
- engine 불문이 원칙(§10 교훈: 하방 보호는 모든 서빙 경로에서)이나, 실측상
  대상은 사실상 v87(앵커는 park 시드라 L 낮음 — 실측 미검증, §7 쟁점 3).

### 1.2 구제 절차 (2단 + 최후 보장)

**①단계 — 0원 대체 (Gemini 0콜, 순수 CPU)**
in-band 후보 전원의 L을 계산(`_spur_metrics` — 폴리라인 순회, ~ms 단위)하고,
L≤800 부분집합이 비어 있지 않으면 그 안에서 기존 서열(`_best_in_band`:
park desc > zigzag asc > retrace asc > 거리 근접)로 재선택 → 서빙.
- 근거: 상한 800 차단 실측 21건 중 20건에 타 스냅 후보 1~6개 존재. 같은 지점
  연속 생성에서 L이 1178→2079→**298**, 3366→**260**으로 출렁인 관측 — 풀 안에
  이미 낮은 L이 있을 개연성. (성공률 정량은 미기록 탓에 산출 불가 — §3에서
  cand_quality에 L을 기록해 이 맹점 자체를 제거.)

**②단계 — 구제 재추첨 (별도 +N롤, 기본 N=5)**
①이 비면 `_adaptive_redraw`(:721)를 **호출부만 다른 동일 루프**로 1회 실행.
- aim은 기존과 동일 산식(실측 ratio 중앙값 블렌드) — 언더슛 조준 문제가 아니라
  형상 문제이므로 aim 보정은 불필요하나, 별도 aim 로직 발명은 오버엔지니어링
  (기존 함수 재사용이 최소 수정). 풀 크기만 `SPUR_RESCUE_POOL_N`(기본 5)으로
  축소 — `_REDRAW_POOL_SIZE=8`(:207)과 독립(주: :726 docstring "5롤"은 상수 8과
  드리프트 — 구현 시 주석만 정정).
- 재추첨 산출물 중 **in-band이면서 L≤800**인 후보만 구제 성립. 도로 등급
  게이트(§8.20, :774-779)는 `_adaptive_redraw` 내장분 그대로 적용.
- 재귀 없음 — 기존 재추첨과 동일하게 요청당 1회 한정.

**③단계 — 최후 보장**
②까지 전패면 {원 후보} ∪ {재추첨 in-band 후보들} 중 **L 최소**를 서빙.
verdict는 원 후보면 "hit" 유지, 재추첨분이면 "hit_redraw" — 기존 어휘만 사용.

### 1.3 기존 8롤 적응 재추첨과의 관계

| | 기존 적응 재추첨(:1198-1240, :1148-1159) | 구제 재추첨(신규) |
|---|---|---|
| 발동 지점 | band_cap_zero(in-band 0) / floor(단독·park0·L>1200) | in-band **hit인데** L>800 |
| 상호 배타 | in-band 유무로 갈리므로 **한 요청에서 둘 다 발동 불가** | 동일 |
| 풀 | 8롤 | 5롤(설정) |

⇒ 요청당 재추첨은 여전히 최대 1회. 요청당 Gemini 상한: 현행 7(풀 9−앵커2) +
2(v2.3 사전 게이트 재추첨) + 8(적응) = 17 → 플래그 ON 시 in-band 경로에서
7 + 2 + **5** = 14 (적응 8롤 경로보다 오히려 낮음. 전체 상한은 여전히 17).

### 1.4 비용 추정 (65건 실측 기준)

- 현 페이스 ~82원/일 ≈ Gemini ~41콜/일(회당 ~2원, §E).
- L>800 in-band hit 빈도: 21건/8일(07-23~30) ≈ **2.6건/일**.
- **상한(①단계 성공률 0 가정)**: 2.6건 × 5롤 × 2원 ≈ +26원/일 = **+32%**.
  (8롤 재사용 시 +51% — 축소 풀 채택 근거.)
- **하한(①단계가 전부 해결)**: +0%.
- 실측 성공률은 §3 관측 필드로 배포 후 정량화 — 비용이 추정 상한을 넘으면
  즉시 보고(§E 규율). 참고: 실측 21건 중 6건은 내부 테스트 계정 생성분이라
  실유저 유발분은 ~1.9건/일 — 위 추정은 보수적(전 계정 기준).

## 2. 서빙 비퇴행 증명 (설계 차원)

1. **경우의 수 전수**: 트리거 미발동(L≤800) → 기존 그대로 서빙. ①성공 → 같은
   in-band 풀의 다른 후보 서빙(서빙 1건). ②성공 → 재추첨 후보 서빙(1건).
   ③ → 원 후보 포함 L 최소 서빙(1건). **어느 가지도 "서빙 안 함"으로 빠지는
   경로가 없다** — 구제 로직은 이미 서빙이 확정된(hit) 요청 안에서만 돌고,
   실패의 종착이 항상 "원 후보 그대로"이기 때문.
2. **예외 봉쇄**: ①②의 모든 예외(재추첨 타임아웃·T-map 실패 포함)는
   try/except로 삼켜 ③(원 후보 서빙)으로 — best-effort 원칙(§D). 신규 raise 0.
3. **에러 계약 불변**: 신규 상태코드·error_code 없음. 502 신규 발생 0(구제는
   hit 경로 내부라 502 분기 자체가 없음). 응답 스키마 변경 없음(gen_meta는
   서버 내부 관측 필드 — 클라 비소비).
4. **_FLOOR_SPUR_M(1200) 패턴과의 관계 — 병존**: floor(:1148-1159)는 [단독
   후보 & park==0 & L>1200]로 조건이 다르나, 플래그 ON이면 구제 트리거
   (L>800, 조건 무관)가 상위집합이라 floor 케이스도 구제가 먼저 잡는다.
   **floor 코드는 건드리지 않는다** — 플래그 OFF 시 기존 동작의 원형 보존이
   롤백 경로이기 때문. ON 상태에서 floor는 사실상 도달 불능이 되며, 관측
   1~2주 후 구제가 안정되면 floor 제거를 별도 판정(재검토 트리거 §6).

## 2.5 안전 게이트 교차 (v113 motorway·램프 하드 차단) — 구현 시 필수 확인 반영

구제가 안전 게이트의 뒷문이 되는 경로는 **구조적으로 없다** — 두 가지 다
기적용 지점을 코드로 확정(2026-07-30 구현 검수):

- **①0원 대체**: 대체 풀은 `in_band ⊂ scored`인데, 후보는 스냅 직후 `scored`
  **편입 전에** 도로 등급 게이트로 폐기된다(`route_service.py`의
  `_road_hit_m(out.path, "hard") ≥ _ROAD_GATE_BLOCK_M` → continue, 메인 스냅
  루프). 즉 대체 후보 전원이 이미 게이트 통과분.
- **②구제 재추첨**: `_adaptive_redraw` 내장 게이트(§10 교훈 — "하방 보호는
  모든 서빙 경로에서", `redraw_road_gate_rejected` 카운트)가 그대로 적용된다.
  구제는 이 함수를 pool_n만 바꿔 재사용하므로 산출물이 게이트를 우회할 수 없다.
- 게이트 차단으로 재추첨 산출물이 0이 되면 ③(원 후보 서빙)으로 — 원 후보
  자체도 메인 게이트 통과분이므로 어느 가지도 미게이트 폴리라인을 서빙하지
  않는다. 테스트 시나리오: 재추첨 스냅에 동해 IC 램프 실폴리라인 주입 →
  내부 폐기 → kept_original 서빙 확인.

## 3. 관측 설계 (gen_meta additive)

서빙 route의 `gen_meta`에 추가(전부 Optional — 기존 소비 무영향):

```
"spur_rescue": {
  "attempted": true,          # 트리거 발동 여부(발동 안 하면 키 자체 없음)
  "mode": "substitute" | "redraw" | "kept_original",
  "rolls_used": 0 | N,        # ①=0, ②=실제 생성 롤 수
  "L_before": 809,            # 원 best의 longest_retrace_m
  "L_after": 260,             # 최종 서빙 후보의 L
  "rescued": true             # L_after ≤ 상한 여부
}
```

- 구제 성공률 = rescued 비율, 비용 = Σrolls_used×2원 — 둘 다 routes 실조회로
  집계 가능(이번 조사와 동일한 방법론으로 재현 가능해야 한다는 게 기준).
- **cand_quality에 `longest_retrace_m` 병기(채택 권고)**: 이번 조사에서 "대체
  가능했는지 K" 산출 불가의 원인이 비서빙 후보 L 미기록. `_spur_metrics`는
  폴리라인 순회 순수 계산이라 후보당 ~ms — 이미 후보별 retrace·max_gap을 같은
  자리(:1120-1123)에서 계산하므로 한 줄 추가다. 이는 트리거 OFF여도 기록되게
  해(관측 선행), 향후 상한 재조정 판정을 실데이터로 만든다.

## 4. 엣지 — dedup과의 상호작용

- **구제 대상 풀은 이미 dedup 통과분**: `_best_in_band`는
  `_split_in_band_dedup`(:1141) **이후**의 in_band에서 고르므로, ①단계 대체
  후보도 전부 소유 지문 회피가 끝난 집합 — 추가 처리 불요.
- **재추첨 산출물은 지문 충돌 불가**: dedup 지문은 앵커 후보에만 정의된다
  (v87은 좌표 발명 층이라 안정 지문 없음 — :476-478 설계 그대로). 구제
  재추첨은 `generate_route`(v87)만 생성하므로 **지문과 교차 자체가 없다**.
  앵커를 구제 풀에 섞는 확장은 하지 않는다(지문 재검사 필요해져 복잡도 증가
  — 트리거될 때만 재검토, §6).
- **천곡 4건 패턴**(커버 지역에서 dedup에 밀려 v87로 온 반복 생성 유저):
  구제 루프 관점에선 일반 v87 hit와 동일하게 동작한다(L 3366→260 관측처럼
  같은 자리 재추첨이 유효했던 바로 그 사례군). 단, 이 패턴의 **근본 원인**
  (캐노니컬 기소유 → 3층 낙하)은 이 설계의 범위 밖 — dedup_exhausted 관측
  스레드(§6 대기 항목)에서 별도 추적.

## 5. 롤아웃

- 설정 3종(`app/core/config.py`, pydantic — ANCHOR_POOL_N 전례):
  `spur_rescue_enabled: bool = False` / `spur_rescue_max_m: float = 800.0` /
  `spur_rescue_pool_n: int = 5`.
- 순서: ①구현+테스트(§6) 후 플래그 **OFF로 배포** — cand_quality L 병기만
  즉시 발효(관측 선행, 무위험) ②`/health` + 코스 생성 스모크 1사이클
  ③`fly secrets set SPUR_RESCUE_ENABLED=true`(머신 재시작 수반 — 512MB 1대,
  수 초 다운타임은 기존 배포와 동일 프로파일) ④스모크 1사이클 + 24h Sentry·
  비용 관측.
- 스모크는 §E dedup 규율 준수: 콜별 소유 누적 사전 시뮬레이션. L>800 유발은
  비결정적이므로 스테이징 실호출로는 **관측 필드 존재/무해**만 확인하고 구제
  로직 자체는 결정적 테스트(§6)가 담당.
- **롤백**: 1차 = 플래그 OFF(코드 원복 불요, 기존 경로 원형 보존이 §2-4의
  병존 설계 이유). 2차 = git revert + fly deploy. DB 마이그레이션 없음
  (gen_meta는 jsonb 내부 키) — 롤백에 SQL 불요.

## 6. 테스트 계획 스케치 (Gemini 실호출 최소화)

전부 `tests/test_spur_rescue_integration.py`, Gemini·T-map은 mock(합성
폴리라인으로 L을 원하는 값으로 조작 — 왕복 팔은 같은 좌표열 왕복으로 결정적
생성 가능), DB 부수효과는 routes 행 gen_meta assert + 종료 시 정리 잔여 0:

1. **미발동**: best L≤800 → spur_rescue 키 부재, 서빙 결과 기존과 동일.
2. **①대체**: best L=1500, 동일 풀에 L=300 in-band 존재 → mode=substitute,
   rolls_used=0, **Gemini mock 호출 수 증가 0 assert**, L_after=300.
3. **②재추첨**: 풀 전원 L>800, 재추첨 mock이 L=200 in-band 반환 →
   mode=redraw, rolls_used=5, verdict=hit_redraw.
4. **③최후 보장**: 재추첨 전패(전 롤 예외) → 원 후보 서빙, mode=kept_original,
   rescued=false, verdict="hit" 유지, **응답 200 + 서빙 1건 assert**(비퇴행).
5. **예외 봉쇄**: 재추첨 중 T-map 예외 주입 → ③으로 강하, 502 없음.
6. **플래그 OFF**: 2·3과 동일 입력에서 기존 동작 그대로(회귀 스냅샷).
7. **floor 병존**: 단독·park0·L>1200 입력 — 플래그 ON이면 구제가 선점,
   OFF면 기존 floor 경로 발동(양쪽 assert).
8. 실호출 스모크는 스테이징 1~2회만(§5 ②④) — 비용 ~4원, 승인 범위 내.
