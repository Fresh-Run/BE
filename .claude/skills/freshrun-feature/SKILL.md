# 새 기능 추가 절차 (설계 우선)

**철학:** 코드부터 짜지 않는다. 설계 문서 없는 큰 작업을 하위 모델로 시작하면
스키마·잠금·엣지에서 무너진다. 순서: **설계 → 승인 → SQL → 구현 → 검증 → 보고.**
전 단계 규칙은 `../../CLAUDE.md`(완료의 정의·알려진 함정·검증 우선)를 따른다.

## 1단계 — 설계 문서 (구현 전 산출)

`docs/`의 기존 설계(예: `RACE_FIX_DESIGN.md`)를 양식 참고로 아래를 채운다:

- **스키마**: 테이블/컬럼/타입/제약. 신규 테이블이면 `enable row level security`
  포함. `information_schema` 실조회로 기존 컬럼명 확인(추측 금지 — CLAUDE.md).
- **RLS + 롤백**: `[APPLY]`/`[ROLLBACK]` 초안(→ `freshrun-sql`).
- **엔드포인트 표**: method · 경로 · 요청/응답 스키마 · 상태코드. 경로 순서
  규칙(고정 경로 먼저) 확인.
- **엣지 케이스**: 권한(404 은닉), 프라이버시, 레이스(원자성 필요 여부),
  하위 호환(additive?), 비용(Gemini 호출?).
- **테스트 계획**: 통합 테스트 시나리오 + assert할 DB 부수효과 + 회귀 목록.

큰 판단(스키마·BM·잠금 전략)은 Opus 이상에서. 확신 90% 미만이면 진행하지 말고
선택지+추천으로 질문.

## 2단계 — 사용자 승인 대기

설계를 제시하고 **명시적 승인 전까지 구현·SQL 실행 금지.** RPC/스키마가 있으면
SQL 블록을 함께 보여 사용자가 Supabase SQL Editor에서 실행하게 한다.

## 3단계 — SQL 출력 (사용자 실행)

`db/<날짜>_<기능>.sql`에 `[APPLY]`+`[ROLLBACK]` 페어로 기록. 우리는 DB에 직접
DDL을 치지 않는다 — **사용자가 Supabase SQL Editor에서 실행**한다. 실행 후
`select ... from pg_proc/information_schema`로 존재 확인 요청. 상세 양식·백필
트릭·RPC 잠금 선택은 `freshrun-sql` 스킬.

## 4단계 — 구현

- `get_supabase_admin()`, 모든 호출 `asyncio.to_thread` 래핑.
- 응답 필드는 기본값 있는 Optional(하위 호환). 기존 엔드포인트 동작 불변.
- 프론트 소비 데이터면 소비 규칙을 코드 주석/설계에 명확히.

## 5단계 — 완료의 정의 체크리스트

`../../CLAUDE.md`의 "완료의 정의" 8항목을 **전부** 통과해야 완료:
신규+회귀 테스트 통과 · DB 부수효과 assert · SQL 페어 · API_GUIDE 소비 규칙 표 ·
키 패턴 grep clean · 임시 데이터 정리 · (스테이징 영향 시) 배포+스모크 ·
보고 양식. 테스트 레시피(프라이버시 이중검증, 404 표준, 레이스 gather)는 CLAUDE.md.

## 6단계 — 보고 양식

- **통과 목록**: 실행한 테스트 파일 + 통과 개수.
- **변경 파일 표**: 파일 · 변경 요지.
- **판단 플래그**: 추측했거나 계획에서 벗어난 지점(스킵·대체·범위 조정).
- **API_GUIDE 반영**: 어느 절을 어떻게 갱신했는지.
